# Agent Spec

## Overview

`city-stroll-agent` creates three compact, taste-matched walking paths for a requested city. Each path focuses on a different neighborhood and contains 5–7 ordered venues spanning shopping, food and drink, and places of interest, targeting roughly 2–4 km of walking.

The first release is a conversational ADK prototype. A single root agent interprets the request, combines it with the user's taste profile, and calls one deterministic `generate_paths` planning tool. The tool—not the language model—handles candidate clustering, compactness filtering, route scoring, ordering, and Maps-link construction. The production target is Vertex AI Agent Runtime with native registration in Gemini Enterprise.

## Architecture

- **Root ADK agent:** Collects the city, optional hotel/station/must-visit anchors, temporary trip preferences, and profile updates; explains the returned alternatives.
- **Deterministic path planner:** Discovers candidate venues, clusters them into distinct neighborhoods, rejects geographically loose clusters, scores taste fit, computes walking distances, and assembles three non-overlapping paths.
- **Profile adapter:** Uses in-memory data in the prototype. Production uses Firestore for the explicit editable taste profile and Vertex AI Memory Bank for preferences learned from conversation only after confirmation.
- **No sub-agents:** Venue discovery, routing, and ranking remain ordinary code and API calls to minimize latency, cost, and coordination failure.

## Planner Interface

`generate_paths` accepts a structured request containing:

- City and country or region.
- Optional start, end, hotel, station, and must-visit place anchors.
- Temporary natural-language tastes and avoidances for this trip.
- The authenticated user's saved taste profile.

It returns:

- Exactly three alternatives when enough data exists, each based in a different neighborhood.
- For each path: neighborhood name, short rationale, estimated walking distance, 5–7 ordered stops, venue category, taste-match explanation, Google Place ID, individual Google Maps URI, route link, and caveats.
- A structured insufficiency result when a city or preference set cannot support three credible paths, rather than inventing venues.

## Example Use Cases

1. **Tokyo fashion and food:** “Give me a Tokyo stroll with independent menswear, excellent ramen, matcha, and one cultural stop.” Return three compact neighborhood alternatives rather than a cross-city best-of list.
2. **Anchored day:** “Start near Shibuya Station and include this specific shop.” Include the anchor where feasible and keep the remaining sequence local.
3. **Profile-assisted request:** “Plan a day in Kyoto.” Combine the sparse request with the user's confirmed cuisine, shopping, atmosphere, and walking preferences.
4. **Profile learning:** “I loved the kissaten suggestions—remember that I prefer traditional coffee shops.” Confirm the proposed durable preference before saving it.

## Tools Required

- **Places API (New):** Text Search, Nearby Search, and Place Details for candidate discovery, supported filters, current venue metadata, Place IDs, and Google Maps URIs. Authenticate server-side with Google Cloud credentials or a restricted Maps Platform key stored in Secret Manager; request only required fields.
- **Routes API:** `computeRouteMatrix` in walking mode for pairwise distances and durations used by the planner. Authenticate server-side and cap candidate matrices to control latency and per-element cost.
- **Maps URLs:** Produce cross-platform place links, a best-effort ordered walking-route link, and per-leg fallbacks because mobile browsers support fewer waypoints than desktop.
- **Profile store:** In-memory adapter for the prototype; Firestore in production, keyed by authenticated Gemini Enterprise user identity.
- **Vertex AI Memory Bank:** Production-only recall of confirmed conversational preferences, adapted from the `cross-session-memory` recipe.

## Data Flow

1. Load the user's explicit profile and confirmed memories; merge them with the current trip prompt without persisting trip-only details.
2. Resolve supplied anchors to Place IDs and coordinates.
3. Search broadly for taste-matched venue candidates, then geographically cluster the results.
4. Reject clusters that cannot form a 5–7-stop path near the 2–4 km target; rank the remaining clusters by compactness first and taste fit second.
5. Select three geographically distinct neighborhoods, compute walking matrices, and order each path with deterministic route logic.
6. Return structured paths to the root agent, which renders concise comparisons, ordered stops, explanations, Maps links, and verification caveats.

## Constraints & Safety Rules

- Recommendations and links only; do not book, reserve, purchase, or initiate navigation.
- Never invent a venue, Place ID, rating, opening status, distance, or Maps URL. Degrade explicitly when an API result is missing.
- Treat dietary, allergy, accessibility, budget, and opening-hour statements as preferences in v1, not guarantees. Tell users to verify safety-critical or time-sensitive details directly with venues.
- Never persist a preference inferred from conversation until the user confirms the exact preference to save.
- Isolate Firestore profiles and Memory Bank data by authenticated user identity; never expose one user's profile or history to another.
- Store durable Place IDs where useful, but do not cache restricted Places content beyond Google Maps Platform policy allowances. Include required Google attribution in rendered results.
- Keep Maps credentials server-side and out of model prompts, responses, logs, and source control.

## Success Criteria

- On each core evaluation case with sufficient venue coverage, return three different neighborhoods with 5–7 real stops per path.
- At least 90% of generated core-case paths fall within the 2–4 km walking target according to Routes API results; every exception is labeled.
- Every stop in evaluation resolves to the returned Place ID, and every individual Maps link opens the intended venue.
- In compactness regression cases, no path crosses between non-adjacent city districts merely to improve taste match.
- Core quality evals judge each path coherent in category sequence, relevant to the stated tastes, and meaningfully distinct from the other two alternatives.
- Automated unit tests cover clustering, compactness filtering, deterministic ordering, malformed/partial API responses, link encoding, and profile isolation.
- Behavioral evals verify that the agent asks before saving learned preferences and clearly labels unsupported safety or opening-hour assumptions.

## Edge Cases to Handle

- Ambiguous city names, anchors that resolve outside the requested city, duplicate or permanently closed venues, sparse Places coverage, and fewer than three viable neighborhoods.
- Routes API partial failures, unreachable walking legs, candidate matrices that exceed configured limits, and Maps URLs that exceed URL-length or mobile-waypoint constraints.
- Conflicting profile and trip preferences; the current trip prompt wins without silently rewriting the durable profile.
